# 04 · AI 使用说明

## 1. 我在项目中承担的角色

这个项目不是“让 AI 生成一个仓库然后直接提交”。我承担的是产品判断、技术取舍、验收和交付把关：

- 决定题目方向、用户场景和 P0 边界；
- 决定哪些能力必须有，哪些明确不做；
- 确认技术选型与失败语义；
- 准备真实依赖并执行关键验收；
- 审查 AI 产出，否掉不可信或不可验证的方案；
- 对前端信息架构、可读性和演示路径提出修改要求；
- 对最终提交内容负责。

AI 承担了大量代码起草、重复实现和排障工作；我承担的是“做什么、为什么这样做、做完是否可信”。

## 2. 我主导的产品判断

### 2.1 先把范围收紧

题目允许做多 Agent、队列、OCR、部署，但这些不会让核心链路更可信。我明确把本轮限定为：

```text
一条可回放的脚本生成链路
+ 五类显式终态
+ 可上传、可检索、可引用的知识库
+ 一个能解释系统的控制台
```

我拒绝为了“看起来完整”加入 Redis、Celery、对象存储和多实例。这些是生产化问题，不是本次验收的核心。

### 2.2 坚持事实边界

我确认：

- P01 只作为合成产品事实，不冒充真实产品文档；
- K01–K80 是合成知识库，不冒充官方资料；
- 没有来源的效果结论不能进入成功结果；
- 没有素材时宁可返回 `NO_MATERIAL`，也不让模型编造。

这不是“模型能不能写”的问题，而是产品是否可信的问题。

### 2.3 知识库的产品取舍

我确认了：

- 支持 PDF/DOCX/TXT/MD/CSV/JSON；
- PDF 只解析文本层，不强行做 OCR；
- 上传成功后自动 active，不做人工审核；
- Parent-Child：短块召回、长块返回；
- reranker 失败重试一次，仍失败则退回 RRF，并记录 `RERANK_DEGRADED`；
- 文档支持下架和永久删除，删除必须清理数据库记录、切片、材料和原文件。

这些决定直接影响了实现范围，也是我和 AI 讨论后拍板的。

## 3. 我主导的技术判断

### 3.1 不用 AgentExecutor 包整条流程

我确认使用 LangGraph 自定义图，而不是把整个流程塞进 `AgentExecutor`。原因是需要：

- checkpoint；
- interrupt / resume；
- 步数与工具预算；
- 可回放的 SSE 事件；
- 明确的失败终态。

模型负责选动作和写脚本，运行时负责边界。

### 3.2 不把“检索”做成一个黑盒

我要求检索结果必须可解释：

```text
BM25 rank
向量 rank
RRF 融合
rerank 分数
Parent 上下文
```

因此系统不仅能返回结果，还能在页面上展示“为什么召回它”。

### 3.3 不假设 rerank 一定有效

我要求做固定 golden set 的 RRF / rerank 对照，而不是只写“已接入 reranker”。  
实际结果是 rerank 在当前 8 条 query 上没有提升，我保留了这个负结果，并在面板和文档中说明。

这体现了我的判断：**评估的价值是发现无效，不是证明有效。**

## 4. 我完成的工程与验收工作

### 4.1 真实环境

我在本机完成了：

- Docker Desktop / WSL2 环境修复；
- PostgreSQL + pgvector 启动与建库；
- `migrate.py`、`seed_data.py` 执行；
- DeepSeek / DashScope 凭据配置；
- 真实 API 启动与接口验证；
- 六种文件格式的上传验证；
- 真实脚本生成与来源检查。

### 4.2 验收标准

我把验收拆成可观察的状态，而不是“看起来能跑”：

| 场景 | 我确认的结果 |
|---|---|
| 正常 30 秒 | `SUCCESS`，引用来源，时长在容差内 |
| 缺关键信息 | `WAITING_INPUT`，不猜值 |
| 无素材 | `NO_MATERIAL`，不生成脚本 |
| 工具失败 | `TOOL_ERROR`，不伪造结果 |
| 超时长 | `UNSATISFIABLE_DURATION`，返回卡点 |
| 入库失败 | `FAILED`，不留下半成品 |
| reranker 失败 | `RERANK_DEGRADED`，显式降级 |
| 删除文档 | DB 记录、切片、材料、原文件同时清理 |

### 4.3 前端与可解释性

我不是只看“页面能不能打开”，而是持续提出可用性要求：

- 正文字号太小，要求整体提高；
- Event Log 看不清，要求放大；
- 增加 Runtime Graph，并高亮当前节点；
- System Map 不能只有几个词，要展示分层、分支条件、工具、Evidence 和 Store；
- Edge Cases 要写清参数和预期；
- 增加知识库上传、切片预览、检索调试和 RAG 评估；
- 增加文档下架与永久删除。

这些修改让评审能看懂系统，而不是只看一个聊天框。

## 5. AI 辅助的边界

AI 帮助完成了：

- 后端主体代码、测试骨架、示例和初版文档；
- 真实依赖报错的定位与修复；
- 知识库、reranker、评估面板和控制台的实现；
- 文档初稿和截图整理。

AI 没有替我做：

- 需求取舍和范围控制；
- 数据真实性与合规边界；
- 失败语义和产品体验判断；
- 真实验收结果的确认；
- 最终提交决策。

## 6. 验证结果

```text
42 passed
六种格式上传 READY
真实 API 生成 SUCCESS
reranker / RRF 对照可复现
```

我没有把 Mock 结果说成真实模型结果，也没有把没有跑过的命令写进文档。

## 7. 能力总结

这个项目体现了我三方面的工作方式：

1. **产品抽象**：把模糊的“生成脚本”拆成事实、时长、规则、失败状态和可回放链路；
2. **技术判断**：在 Agent 框架、RAG 粒度、reranker、知识库边界上做取舍，而不是堆功能；
3. **验收意识**：用真实环境、固定 case 和可解释指标验证结果，接受不符合预期的结论并继续修正。
