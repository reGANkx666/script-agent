# 05 · 复盘

## 1. 我遇到的典型问题

这些问题不复杂，但在真实环境里很容易卡住进度。我把它们当成“工程基本功”的一部分处理。

| 问题 | 现象 | 我的处理 | 结果 |
|---|---|---|---|
| Docker 启动失败 | 一直停在 Starting the Docker Engine | 确认不是 Hyper-V 单独能解决，而是缺 Virtual Machine Platform；启用 VMP/WSL 后重启 | Docker 正常启动 |
| 端口被旧进程占用 | 启动 API 报 `10048`，新进程无法绑定 | 用 `netstat -ano` 定位旧进程，停止旧实例后重启 | 服务恢复，避免重复进程 |
| 数据库端口冲突 | 本机 PostgreSQL 已占用 5432，Docker 映射失败 | 将 Docker 映射改为 5433，并同步修改 `DATABASE_URL` | 迁移和种子正常 |
| 终端中文乱码 | PowerShell 输出中文变成乱码，看起来像数据损坏 | 确认是终端编码问题；文件与 API 使用 UTF-8，检查时改为文件读取或设置编码 | 结果可读，不再误判 |
| 文件格式差异 | PDF/DOCX/CSV/JSON 结构不同，不能一套规则硬切 | 按格式分别解析：PDF 文本层、DOCX 标题/段落、CSV 一行一条、JSON 一条记录 | 六种格式成功入库 |
| 前端信息密度过高 | 评审反馈字号小、Event Log 看不清、System Map 只有几个词 | 放大正文字号，增加流程图、分层架构、分支条件、工具/Evidence/Store 细节 | 页面可读性和解释力提升 |
| rerank 结果不符合预期 | 接入 reranker 后，固定评估集上的 MRR 反而下降 | 不隐藏结果；增加 RRF / rerank 对照面板，记录 wins/losses | 形成可复现的评估结论 |

## 2. 真正难的不是“把功能做出来”

### 2.1 范围控制

题目很容易让人想加：

```text
多 Agent
Redis / Celery
对象存储
OCR
多实例
```

但这些不会让核心链路更可信。我选择先保证：

```text
一条可回放的生成链路
+ 五类明确终态
+ 可上传、可检索、可引用的知识库
```

这是我做得最对的一个判断。

### 2.2 事实边界

“生成一段看起来不错的脚本”不难，难的是：

- 每个产品事实有来源；
- 口播包含 claim 原文；
- 没有效果数据时不能写“提升 80%”；
- 没有素材时不能编造。

我宁可让系统返回 `NO_MATERIAL`，也不接受一个“看起来很完整但事实是假的”结果。

### 2.3 检索粒度

一开始知识库只有短素材，检索精确但上下文不足。

后来选择 Parent-Child：

```text
Child：短块召回、事实引用
Parent：长块上下文、Writer 理解
```

这让我理解到：RAG 不是“接一个向量库”，切片粒度、召回单元、返回上下文和引用粒度必须一起设计。

### 2.4 评估可能给出负结果

我要求做 RRF / rerank 的固定集对照。实际结果是：

```text
RRF MRR 0.85
rerank MRR 0.73
```

rerank 没有提升，反而在 3 条 query 上下降。

我没有改数据让它“看起来更好”，而是把这个结果保留在面板和文档里。  
这让我接受了一件事：**评估的价值是发现无效，不是证明有效。**

## 3. 面试时可以展开的三条

### 第一条：为什么不用 AgentExecutor

因为需要 checkpoint、interrupt、预算和可回放事件。模型可以选动作，但不能自己决定流程终点。

### 第二条：为什么短块召回、长块返回

短块提高检索精度，长块补上下文；引用仍然落在短块事实，避免 Writer 把整段 Parent 当事实。

### 第三条：为什么接受 rerank 负结果

因为评估面板显示 rerank 在当前 golden set 上没有提升。保留负结果，才能继续决定是改输入、调阈值，还是关闭 rerank。

## 4. 做得不够的地方

- 入库任务仍是进程内 `asyncio`，API 重启会丢正在执行的任务；
- 原文件存本地 `uploads/`，不是对象存储；
- PDF 没有 OCR，扫描件无法入库；
- 81 条 seed 素材没有包装成独立的 seed document；
- reranker 还没有做输入改写、阈值和候选池调优；
- 没有 CI、Docker Compose、鉴权和多实例；
- 前端是原生静态资产，没有组件测试。

## 5. 如果再做一次

```text
1. 先固定知识库快照和 golden set
2. 再做检索 / rerank 评估
3. 再做 UI
4. 最后补生产化队列和对象存储
```

这次是先做功能、再做评估；如果重来，会先有评估基线，避免“功能看起来完整，但不知道检索是否变好”。

## 6. 学习收获

- 可靠性主要来自运行时边界，不是模型本身；
- 真实环境会暴露端口、编码、数据库、文件格式这些“非 AI 问题”；
- RAG 的召回单元和引用单元必须一致；
- 评估指标可能和直觉相反，必须保留并解释；
- 演示项目和生产系统之间，差的不是功能数量，而是任务持久化、存储、并发和运维。
